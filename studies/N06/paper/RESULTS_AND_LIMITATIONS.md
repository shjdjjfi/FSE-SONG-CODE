# N06 — Experiment Results (controlled synthetic mechanisms only)

**Measured on November 15, 2026.** The experiments in this report were actually
executed, but every event trace was generated by `src/simulator.py`; the two
upstream rule repositories were source configurations, not observed field
deployments.  **This is not a completed FSE empirical evaluation.**

## 1. What was run

- **Original, preregistered model variant (`owner_relink`)**: 2 source-derived
  `for` durations (10 and 15 minutes), 11 synthetic scenario families, seeds
  17/29/43, 30 episodes per cell = **1,980 episodes**.  10 policy arms,
  **19,800 paired episode-policy records** and complete gzipped event streams.
- **Post-hoc variant (`owner_relink_v2`)**: designed *after* original-run
  diagnostics.  Tested on separate synthetic seeds 101/211/307 with another
  **1,980 episodes**, 11 arms and **21,780 episode-policy records**.  No
  parameter tuning is performed inside this evaluation.
- **Unit validation:** 14 Python `unittest` cases passed, covering reset
  semantics, oracle isolation, deterministic generation, source-rule durations,
  unrelated-owner refusal and no-event continuity refusal.
- **Restricted YAML cross-check:** 4 handcrafted tests / 7 assertions passed
  against a purpose-built reference evaluator; two generated owner cases are
  ready for official `promtool`.  This is **not a native Prometheus engine
  result**. The attempted native command returned exit 2: `promtool` absent.

## 2. Primary outcomes, first-run seed set (17/29/43)

| Alert method | Recall on positive synthetic episodes | False-page rate on negative synthetic episodes |
|---|---:|---:|
| Per-pod instance identity | 31.1% | 20.0% |
| Service aggregation + 90 s bridging | 99.9% | 32.3% |
| Service ratio (>10%) + 90 s bridging | 99.9% | 32.6% |
| Owner aggregation + 90 s lookback | **91.8%** | **12.3%** |
| Event-verified owner relinking (`owner_relink`) | **75.4%** | **3.6%** |
| Relinking without black-box probe veto | 75.4% | 8.2% |
| Probe-only TTL | 96.6% | 24.2% |

The original method favors precision but clearly sacrifices recall. Its
greatest synthetic weaknesses are missing owner metadata (0% recall) and
rollout-event clock skew (65.6% recall vs 100% for owner+lookback).  A strict
event-only relink policy cannot be represented as a universally superior
solution by these results.

**Falsification examples:**

- In 180 synthetic *different-owner same-name* cases, the naive
  `service_grace` baseline falsely pages in 180/180; owner-aware methods page
  in 0/180.  This is a deliberately stress-tested construction, not a
  production frequency estimate.
- In 180 synthetic *silent recovery without rollout* negatives, owner lookback
  falsely pages in ~43.9%, whereas strict relinking avoids them in this
  generator.  The difference relies on knowing that no verified rollout was
  present and must be retested with actual missing rollout events.
- In true outages with no metric churn, stable service grouping and owner
  grouping have identical 100% recall; sophisticated relinking adds no benefit.

## 3. Exploratory improvement and separate fresh synthetic seeds

`owner_relink_v2` adds two mechanisms based on original-run failures:

1. Cache a known Pod→owner relation, including the mapping from a verified
   rollout event, when individual metric samples omit owner metadata.
2. Allow bounded continuity for an otherwise unexplained short gap if a recent
   **observed** (not oracle) black-box probe reported service unavailability;
   this intentionally trades some extra false alarm risk for reduced misses.

On new synthetic seeds 101/211/307:

| Method | Recall | Negative false-page rate |
|---|---:|---:|
| Owner+lookback strong baseline | 92.2% | 11.7% |
| Strict event owner relink v1 | 76.9% | 3.2% |
| **Owner relink v2, post-hoc** | **94.2%** | **11.1%** |
| Probe-only TTL | 96.4% | 26.2% |
| Service+grace | 100.0% | 31.7% |

Against owner+lookback in these *generated* episodes, v2 rescues **21 of
1,080** positive cases that the baseline misses, loses **0** positives which
the baseline detects, and fires at least one 15-second evaluation earlier in
**30 of 996** episodes both detect.  Across 900 negative episodes, v2 reduces
the false-page episode count by **5** (a small effect).  Stratified paired
Monte Carlo intervals (conditional on the fixed generator) are:

| Pairwise difference v2 − owner+lookback | Point difference | Conditional 95% Monte Carlo interval |
|---|---:|---:|
| Positive detection recall | +1.94 percentage points | +1.20 to +2.69 pp |
| Negative false-page episode rate | −0.56 percentage points | −1.11 to −0.11 pp |

The new-seed benefit is concentrated in missing-owner cases: v2 achieves
65.0% positive recall versus 53.3% for owner+lookback.  Both remain fragile
under substantial metadata loss.  The benchmark distribution is invented;
these intervals **cannot be called project-clustered confidence intervals or
field generalization evidence**.

## 4. Sensitivity and failure analysis

The original-run 90-second grace corresponds to six 15-second evaluations.
On a 20%-sampled synthetic sensitivity grid:

- At 0-second grace, both strict relink and owner lookback only detect ~31.0%
  of positive episodes, with zero false-page episodes in the sample.
- At 90-second grace, original relink recall is ~75.9%, false-page rate ~1.1%
  on negatives; owner lookback is ~92.6% recall and ~7.8% negative false pages.
- Lengthening the grace beyond 90 seconds increases recall only slightly for
  the original event-based variant, while alternative owner+lookback retains
  its own precision–recall tradeoff.

See `results_v2/grace_sensitivity.csv` for the entire grid and exact sampled
denominators. It is a sensitivity analysis of the constructed generator only.

## 5. Main validity threats

1. **No production trace:** No real timestamped joint set of `Pod UID →
   ReplicaSet → Deployment UID`, rollout records, TSDB samples and independent
   probe outcomes was available for this run.  Neither of the two source
   repositories is a measured SRE rollout case study here.
2. **Simplified semantics:** The Python model implements only the `for` clock
   and emitted boolean conditions.  It does not run real PromQL, lookback,
   staleness markers, recording rules, `keep_firing_for` behavior, rule loading
   or Alertmanager.  Native `promtool` is absent.
3. **Different operational contract:** Original `TargetDown` is `>10%` target
   outage by stable job/namespace/service; original `KubePodNotReady` reports
   individual Pod readiness. The *study* oracle instead defines sustained
   **owner-scoped service** outage.  It would be invalid to call the output
   an exact comparison of these unmodified upstream alert rules.
4. **Generator coupling:** Observed probe values are derived (with dropout)
   from the generated ground truth.  They are not truly independent real
   measurements; reliable samples may disproportionately aid probe-aware
   policies.  Missing owner metadata and rollout-latency distributions are
   assumptions, not measured rates.
5. **Tuning and selective outcome:** v2 was designed after primary outcomes;
   despite newly seeded synthetic validation, it requires a frozen independent
   **real-project** holdout before any credible industrial effectiveness claim.
6. **Prior art:** Existing publicly available chart code already supports
   Deployment-level alerts across pod replacements and describes
   `max_over_time` continuity.  The remaining novelty is the particular
   *verification/veto* policy and evidence boundary, which is unvalidated in
   a native monitoring stack.
7. **No operational effect:** No SRE page delivered, no false resolution
   observed, no service in Kubernetes deployed, and no exporter memory or CPU
   overhead measured.  Python runtime is not a production cost estimate.

## 6. Bottom line

**The N06-v2 idea remains plausible but unvalidated for FSE 2027 Industry.**
Synthetic data supports a small improvement over owner+lookback under one
frozen generator, and strict v1 demonstrates a detection–false-alarm tradeoff.
The central real-world causal and industrial-value claims remain unanswered.
Do not submit these simulated results as a completed empirical paper.  See
`SUBMISSION_BLOCKERS.md` for an exact remaining evidence checklist.
