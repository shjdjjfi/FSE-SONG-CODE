# N04：测试身份变更后 Flaky 历史继承——完整实测报告

**实验对象**：所附七题清单按展示顺序的第 3 个，即 N04 *Recovering Flaky Test History Across Test Identity Changes*。不是编号 N03。

**执行日期**：2026-11-14 至 2026-11-15；**研究场景**：FSE 2027 Industry Track。**硬件要求**：CPU，无 GPU、无商用模型 API。所有结论依据此包的实际冻结数据，未把模拟结果称为生产 CI 事实。

> **总判断：已经完成大量公开数据实验、真正的历史代码前后回放与独立基线检验；尚未达到 N04 原提案所设的论文投稿证据门槛。** 最强简单基线恢复率已经是 96.44%，因此同一基准上不可能额外提升原定的 15 个百分点；独立真实 quarantine / CI 历史转移日志仍未取得。详见 `UNRESOLVED_SUBMISSION_GAPS.md`。不建议将当前结果写成“提出的方法显著优于强基线并在真实 CI 降本”的结论。

## 1. 原始主张及可证伪指标

研究问题：当测试在 Git 提交中更名、迁移、换参数 ID 或拆分时，旧测试的 flaky 历史应该保留、拒绝或弃权？错误重接可能误隔离；完全重置会丢失历史。

原始提案的成功条件是 **错误继承率不超过 2% 时，恢复率比对照提高至少 15 个百分点**。工业版本还应有：真实 CI 报告、两个版本的可确认身份真值、独立 quarantine 决策/结果、跨项目时间留出、拆分与语义变更负控以及可追溯成本。

本次冻结了四类证据：

| 证据层级 | 数据 | 实际观察 / 干预边界 |
|---|---|---|
| A：真实历史源码标签 | TestMigrationsInPy，不同开发者写出的 Python unittest→pytest 转换 | 原项目真实前后源码；随机候选和“移除正确目标”是受控构造 |
| B：真实运行工具行为 | pytest 7.4.4、8.4.2、9.0.1；5 种受控变更 | 真正执行 pytest 收集和缓存操作；fixture 由本研究创建，不代表真实 flaky |
| C：公开真实测试结果 | FTW 2024 的 30 次重复运行数据，覆盖 8 个开源项目 | 真实 pass/fail；假设历史重置或继承只在离线分析中模拟 |
| D：真实 Git 修订前后重复执行 | Java-WebSocket 的 2018 年实际重构提交，40 对 JUnit 测试 | 真正分别执行重构前后各 30 轮；映射由源码提取；没有真实 quarantine 日志 |

## 2. 数据审计：真实标签与纳排标准

### 2.1 Python 迁移语料

固定 `TestMigrationsInPy` 源码提交 `d29ae2370ee5d7ef81e78421c1f1d7f7b753c04c`。所下载快照中数得 932 个 `mig*-before-*` 文件条目，而论文和仓库 README 使用 923 的总数：两者**口径不一致**，不人为改写为一致。

本实现只选能够从前、后源码各解析出一个测试定义且在同次提交中标识唯一的配对。审计计数：55 组非单测试代码片段被排除，2 组身份重复被排除，余 **875 个可配对测试变更、13 个工程、108 个提交**；其中 33 组在同提交无其他可选目标，因此不进入需要竞争候选的主要评价。主基准为 **842 个迁移查询/种子**，3 个种子各 842 条，共 2,526 次查询计数；它们并非 2,526 个独立迁移事件。

每个查询候选包含同一提交中的真实其他测试，候选数为 2–12，均值 9.99。为检验“目标已经删除/无法迁移”，再构造一份移除正确候选的反事实集合。真实标签是语料本身的前后配对；**目标不存在的反事实不是历史真实删除事件**。模型只见旧片段与候选片段，不见用于评测的已知配对索引。

### 2.2 Flaky 测试标签与重复执行数据

从 IDoFT 固定提交 `4903dc9233eead4e4191c66f9ed0b14eea091052` 读取：Maven 8,075 行（其中 245 个 `MovedOrRenamed`、34 仓库）、Gradle 1,029 行（其中 1 个）、pytest 1,618 行（其中 2 个）。Maven 的 245 个身份变更标签中 216 个含明确的 Git 提交链接。独立数据源和文件哈希见 `DATA_SOURCES_AND_LICENSES.md`。

从 [FTW 2024 的 Zenodo 归档](https://doi.org/10.5281/zenodo.10639030) 实际解析 330 个压缩表、**4,654,230 行执行结果**，覆盖 8 个开源项目。归并后得到 149,110 个 test×commit 键；其中 **148,211 个有完整、非 skip 的 30 次结果**：126,619 个恒通过、20,551 个恒失败、1,041 个既通过又失败。以上统计单位都是测试×提交快照，**不是**互不相关的测试方法数或项目数。

## 3. RQ1：跨项目身份恢复——8 臂公平比较

采用 leave-one-project-out：每次只用其他工程校准置信阈值；错误继承目标为 2%，但这只是训练侧经验目标，不能保证每个测试工程低于 2%。种子 `17/29/43` 变化候选采样；不按测试行随机打乱项目。主要指标：

- **正确恢复率**：有真实正确目标的查询中，方法明确指向正确测试的比例。
- **合并错误继承率**：目标存在时错接别的测试，以及目标被移除后仍指向某测试，按两类等量受控查询合并计算。
- **选择性精度**：在实际给出链接的预测中，正确链接所占比例。

| 方法 / 消融 | 恢复率 ↑ | 合并错误继承率 ↓ | 备注 |
|---|---:|---:|---|
| Exact node ID | 30.76% | 0.00% | 保守，丢失大量变更历史 |
| **Method name（最强简单基线）** | **96.44%** | **0.71%** | 符合本基准所定 2% 风险条件 |
| File + method | 95.72% | 0.71% | 强工程基线 |
| Source similarity | 51.86% | 3.35% | 超过 2% 风险 |
| **Semantic anchor（研究候选）** | **49.01%** | **3.19%** | 弱于强基线且超风险条件 |
| Semantic anchor w/o assertion | 64.77% | 2.14% | 消融；仍超风险条件 |
| Semantic anchor w/o context | 43.67% | 2.75% | 消融 |
| Post-hoc hybrid（探索性） | 95.72% | 1.19% | 看过初测结果后设计，不作确认性胜利宣称 |

**核心负结果**：Semantic anchor 比 `method_name` 低 **47.43 个百分点**。按 13 个项目重抽样的该差值 95% 区间为 **[−69.48, −27.37] 个百分点**。即使加入完美 oracle，`method_name` 的 96.44% 已使该数据上的最大提升仅有 **3.56 个百分点**，原要求的 +15 个百分点数学上不可能达成。项目聚类区间衡量跨项目变动；种子不是新的独立项目。

### 3.1 复杂身份变更子集

在 875 个可配对事件中，出现 25 个方法名变更、609 个类名变更、227 个文件名变更（可重叠）。842 个主评价事件中仅 **20 个真实方法改名事件，来自 3 个项目**。在这 20 个上，Semantic anchor 恢复 **50.00%**，Method name **0.00%**；这里方法名基线按定义无法重接，说明语义信息有潜力；但该子集非常小，且没有通过额外工业项目验证，也不能推翻总体显著落后这一结果。

`results/analysis/identity_change_subsets.csv` 包含上述所有类型的逐方法分层表；`per_project.csv` 保留每项目结果。项目聚类 bootstrap、三种子逐项指标见 `analysis.json`、`per_seed_primary.csv`。对 4 与 20 个最大候选的敏感性实验在 `results/robustness/k4/` 与 `k20/`：两种 K 下方法名基线恢复率都为 **96.44% / 错误率 0.71%**；Semantic anchor 在 K=4 时为 **43.59% / 1.72%**、K=20 时为 **49.05% / 3.21%**。K 不同的结果未单独校准成相同的实际错误率。

## 4. RQ2：在三个 pytest 版本上真实复现工具行为

在 Python 3.12.14 上分别用 pytest **7.4.4、8.4.2、9.0.1** 实际执行初次失败、改动前 `--lf --lfnf none --collect-only`、改动后选择、缓存映射修复后选择、空缓存负控。每个版本都完整完成下表：

| 受控变更 | 改动前 --lf 收集 | 改动后 --lf 收集 | 严格 bridge 后 --lf 收集 | Bridge 行为 |
|---|---:|---:|---:|---|
| 函数改名 | 1 | 3 | 1 | 仅通过 AST 主体相同进行 1:1 重接 |
| 文件搬移 | 1 | 3 | 1 | 仅通过确认的文件移动重接 |
| 参数 ID 变化 | 1 | 3 | 1 | 值与参数索引唯一时重接 |
| 断言语义改变 | 1 | 1 | 0 | 不继承；旧失败记录被移除 |
| 1→N 拆分 | 1 | 4 | 0 | 歧义时拒绝继承 |

所有三版本的空缓存对照收集 **0**。此实验是真正的 pytest 进程与缓存文件操作，而**初始失败是确定性 fixture 断言失败，不是自然 flaky**。这说明机制能工作，不能外推生产环境 quarantine 降本。脚本和每次标准输出保留在 `src/pytest_behavior.py`、`results/pytest_behavior/`。

## 5. RQ3：真实 30× 测试结果上的历史丢失反事实

对 148,211 个完整 test×commit 单位的 30 次实际结果，按三个种子打乱重复执行顺序，以部分结果作为“过去”，10 次作为“未来”，离线模拟“保持 ID”及“迁移时重置 ID”。测试结果本身**没有合成、没有修改**；“发生了重命名/重新隔离、或实际执行了 quarantine”并不存在于原数据，是本研究施加的反事实假设。

| 种子 | 后 10 次中观测 flaky | 保留旧历史时遗漏 flaky | 身份重置时遗漏 flaky | 新增遗漏数 |
|---|---:|---:|---:|---:|
| 17 | 521 | 202 | 347 | 145 |
| 29 | 533 | 210 | 377 | 167 |
| 43 | 536 | 217 | 355 | 138 |

以 8 个项目作为聚类重抽样单位，模拟身份重置导致未来 flaky 漏检比例增加 **28.30 个百分点**，95% 区间 **[10.14, 31.40] 个百分点**。这一差异支持“历史丢失可能有代价”的研究动机，但**不是某个身份恢复算法的实际效果**。另将源本已 flaky 的隔离状态错误复制给稳定目标，可人为诱发 811/807/815 例（每种子 1,038 个构造反事实候选）的误隔离；该数字是**在指定错误连接前提下的后果**，不是算法自身真实误接率。

## 6. RQ4：Java-WebSocket 真实维护提交的跨版本 JUnit 回放

使用 Java-WebSocket 的真实父提交 `27e26758d6604f5d078709233028bb87b4a39e16` 和重构提交 `2ce6e6149d0ef44f4919e75326265c64c144a00f`。开发者把 `Issue256Test`、`Issue580Test` 中共 40 个编号测试转换为 **4 个测试方法×每个 10 个 JUnit 参数实例**。先只根据前后源代码的 helper 调用、参数值和编号推断关系，得到 **40/40** 的实例映射，再独立比对 IDoFT，命中其 27 条已标注 moved/renamed 测试 **27/27**。这是**单仓库、单提交**，没有把规则称作已跨项目验证。

历史 FTW 资料中，这 27 个旧编号测试真实出现于 **2,020 个测试×提交快照**，其中 **102 个单元在 30 轮内既成功又失败**，提供了变更前多提交的真实 flaky 背景。但这个归档没有重构后对应的 30 轮结果，因此又对真实 Git 前后两版独立进行了本地 JUnit 重跑。

**实际部署前后运行方案**：JDK 8 编译旧版 Java 6 目标代码，Maven 3.9.11 / Surefire 3.2.5 在同一 Linux 主机用 Java 21 运行两个真实 test 类，每版 30 轮，每轮 40 个测试。汇总：

| 真实重复执行 | 重构前 | 重构后 |
|---|---:|---:|
| JUnit 测试实例 | 40 | 40 |
| 完整执行轮数 | 30 | 30 |
| 真实测试实例运行总数 | 1,200 | 1,200 |
| 失败/错误（非通过）总次数 | 11 | 6 |
| 至少一次通过且至少一次失败/错误的实例 | 5 | 6 |

按源码链接的 40 对测试中，重构前后均 flaky **3** 对、仅重构前 flaky **2** 对、仅重构后 flaky **3** 对、两边都不 flaky **32** 对。由于仅涉及一个提交且存在真实的 socket 时间依赖、共享服务状态和非随机化运行顺序，**11→6 不能归因于映射/重构方法的因果改进**。

模拟“前 20 次的隔离决定是否转移到后版本未来 10 次”时：种子 17/29 的未来 flaky 分别有 2 个，保留历史漏掉 1，重置历史漏掉 2；种子 43 的未来 flaky 有 1，保留和重置都漏掉 1。它仍是**使用真实执行结果计算的离线决策回放**，从未读取生产 CI 的隔离 API 或流水线日志。所有两版 2,400 条逐实例真实结果、30 次日志和身份对照表均已冻结。

## 8. 结果解释与投稿决定

**被实验支持的结论**：

1. pytest 按节点 ID 保留 last-failed 记录时，真实改名/文件迁移/参数 ID 改变可以使选测退化；严格、保守的 AST 映射能在受控案例恢复记录并在拆分时弃权。
2. 真实开源测试的重复运行具有足够多的跨轮 flakiness，历史重置的离线模拟确实损失分类能力。
3. 一次真实 Java 参数化重构可以在源码和独立 IDoFT 标签下形成可核对的 40 条身份链接，且前后都能实际运行。

**被实验否定或不能支持的结论**：

1. Semantic anchor **未**在主要跨项目公开基准胜过简单名称基线，也未达到 ≤2% 错误率；原始 +15pp 成功标准不成立。
2. 不能声称“生产 CI 隔离成本降低 xx%”：缺少真实的隔离/解隔离事件或生产流水线对照。
3. 不能声称“通用 Java 迁移器达到 100% 准确率”：40/40 仅来自一处真实重构且特殊编号格式。
4. 无法根据 8 个历史项目的模拟身份重置推断实际历史 rename 发生频次；没有用多项目时间切分验证算法。

因此当前最诚实的论文定位是“**可复现的机制与公开真实数据反事实研究，算法主张负结果**”。如坚持 FSE Industry Long 主线，应该按下一份文档的 STOP/GO 门槛补外部证据并重新设计方法，而不是扩张指标口径。本文所有统计均可在 `results/` 对应表中追查。
