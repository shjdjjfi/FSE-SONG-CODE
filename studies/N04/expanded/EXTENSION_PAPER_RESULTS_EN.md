# N04 supplemental Results and Threats (2026-11-15)

**Research status: empirical extension, not a submission-ready positive industry deployment claim.** This supplement must be read alongside `PAPER_RESULTS_EN.md` and the experiment ledger. All actual Git revisions, public PR/MR links, and local test outcomes are recorded; claims are explicitly separated from developer statements, counterfactual replay, and post-hoc model selection.

## RQ1. What quarantine-management events can be independently established?

We verified the merged source changes, timestamps, and relevant test annotations in six GitLab merge requests and three Microsoft Aspire pull requests, each through public repository metadata and diff evidence. In GitLab, [!162803](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/162803) quarantined the RSpec `reverts a merge request in a new merge request` on August 19, 2024; [!163832](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/163832) modified the Sidekiq-in-transaction check implicated in JS feature-spec false positives on August 26; and [!164022](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/164022) removed the same test's quarantine annotation on August 27. We independently verified the exact test description and file path in the paired source diffs. The developer's explanation of the causal defect is recorded as such, not remeasured as a production test outcome.

In an independent C# ecosystem, the merged Microsoft Aspire [PR #13874](https://github.com/microsoft/aspire/pull/13874) describes unquarantining 25 tests after 159 stable runs, and [PR #14040](https://github.com/microsoft/aspire/pull/14040) describes 11 tests following 215 stable runs. We observed 17 and 11 removed `[QuarantinedTest]` annotation lines respectively (additional PR #9023 removes four); test counts need not match attribute-line counts because some tests are parameterized. The repeated-run numbers are maintainer statements: raw per-test job logs were not accessible. We cannot estimate post-unquarantine failure rates, time saved, or a causal benefit of a history-migration algorithm from these records. The subject intervention was **not deployed into any upstream CI**.

## RQ2. Does a source-informed lineage matcher outperform the strongest practical trivial baseline?

The frozen Python TestMigrationsInPy benchmark includes 842 evaluated source-to-source test pairs per seed, 13 projects, three seeds and project-held-out threshold calibration (2,526 positive queries and 2,526 controlled target-absent negatives). The original exact-method-name baseline obtains 96.44% recovery with 0.71% combined erroneous-transfer rate. A newly measured stronger **simple** baseline resolves same-name collisions by source similarity: **97.39% recovery, 0.71% erroneous transfers**. A two-stage method that first performs this resolution and then selectively accepts case/underscore-normalized renames with sufficiently similar token and sequence evidence yields **98.22% recovery and 0.71% erroneous transfers** (2,481 versus 2,460 correct of 2,526; +0.83 percentage points). A more permissive body-only fallback yields 98.34% recovery but increases erroneous transfers to 0.93% and the five-to-one transfer-error cost from 0.089 to 0.110. An independently implemented conservative fall-through model with 97.86% recovery has an even worse 1.27% false-transfer rate and five-to-one cost of 0.148.

The project-cluster paired bootstrap confidence interval for the 98.22%-versus-97.39% comparison is **[0.00, +5.69] percentage points** (13 project clusters). It includes zero, and the model family itself was formulated after the original corpus was inspected. Thus this is an **exploratory improvement**, not independent confirmatory superiority. Moreover, an absolute +15 percentage point recovery target is impossible on a benchmark whose baseline already reaches 96.44%; its mathematical headroom is only +3.56 points. No claim of novelty against the published TestRefactoringMiner is justified without executing a true like-for-like Java baseline.

As a complementary independent-domain stress probe, we read the [ICPC 2021 annotated test-method-name-evolution data](https://zenodo.org/records/4608143), which contain 398 appearances of **293 unique refactoring IDs** across seven relevant XLSX sheets. On hard-name, 16-candidate controlled pools and five refactoring-ID folds, name normalization obtains 20.82% recovery and 0.68% false associations; lexical edit similarity 55.97% and 2.56%; a negation-vetoed lexical hybrid 56.66% and 2.05%. Fifteen renames contain lexical negation-polarity changes, illustrating why name continuity alone cannot certify semantic continuity. However, these tables do not include executable original test bodies or project identifiers, so this probe **cannot** validate the source-aware method, guarantee cross-project independence, or label whether a quarantine state is safe to inherit.

## RQ3. Can observed historical test splits and semantic changes be replayed outside the original Java case?

We pinned, checked out, and executed historical `pallets/click` and `pallets/markupsafe` revisions under Python 3.12/pytest 8.4.2. Across **four different historical change events**, both before/after revisions were exercised ten times, giving **80 local pytest invocations and 4,990 archived individual JUnit test-case outcomes**, all invocations exiting successfully. The cases were: a real one-to-two **test-method split** (`click@7c7ec36`, one old test to two new tests), a **test-module split** (`click@7ecc8d7`, 75 tests in the selected old file versus 67 in the selected new directory per run), a second module split (`click@9ab346f`, 148 versus 148 selected cases per run), and a **same-name semantic extension** (`markupsafe@e49d257`, 24 passed/5 skipped per run in each revision). Source AST comparison independently confirms the nested-resource logic was removed from the original Click test and placed in the newly added test. It also verifies 32 unique unchanged-function-body correspondences across files in the `click@9ab346f` module move.

A conservative 1:1 transfer policy should abstain for the true one-to-many split. The unchanged name in the MarkupSafe case must not be interpreted as automatically unchanged semantics; the test gained additional multiline HTML cases. However, the MarkupSafe change does **not** establish that carrying earlier failure history is wrong, nor did our executions observe such a mistake in a CI system. Together with the existing Java-WebSocket study (2,400 real JUnit test-case outcomes around a pinned historical conversion), the release now contains **7,390 locally observed executions across three repositories**, not 7,390 independent test migrations. These runs are genuine source/version tests, not the historical upstream CI logs.

## Threats, boundaries, and paper go/no-go

1. **Outcome missingness.** Public GitLab/GitHub changes verify operational decisions but do not expose a complete test-level stream of failures, quarantines, unquarantines and follow-up executions. Github issue API rate/access blocks and protected GitLab notes were not bypassed. Developer-cited repeated runs are not independent raw measurements.
2. **Pre/post external validity.** Local pytest is a real process using real source revisions, but is not the original project's CI environment; source migration semantics may depend on fixtures, OS, plugin versions or workloads. The four events span two Python repositories under one organization plus the earlier independent Java repository.
3. **Selection/model leakage.** Additional matching strategies were selected post hoc. Leave-one-project-out threshold calibration cannot cure post-hoc architectural selection. The positive 0.83-point gain over a new strong trivial baseline has a project-level interval containing zero.
4. **Name-only independent data.** The ICPC Excel names are real refactoring annotations, but the negative candidate pools are constructed and the ID folds may mix underlying projects. The full original 1.8 GB SQLite source/commit index was not accessed.
5. **Semantic safety and causality.** A real source-level test split supports abstention on an unsafe 1:1 inheritance interpretation, but neither a real bad quarantine transfer nor its production consequence was observed. Real FTW repeated test outcomes from the original N04 package are used only in counterfactual history-reset analyses.
6. **Prior-art comparison.** Unchanged-AST or body similarity is an established approach in test/refactoring mining. No statistically robust differentiator against an implemented RefactoringMiner/TestRefactoringMiner baseline or production quarantine system is yet demonstrated.

**Decision:** These are defensible feasibility, negative-result and source-historical findings. They do **not** support the intended FSE 2027 Industry Track claim that a deployed test-history transfer method substantially improves real CI quarantine management. A confirmatory submission of that claim requires accessible longitudinal per-test action/outcome records and a newly sealed, genuinely challenging held-out benchmark with directly runnable strong prior-art baselines.
