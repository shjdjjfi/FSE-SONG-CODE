# FSE 2027 Industry Track：N21 实验交付与投稿证据核查

*截至 2026-11-18；本文件依据本包内原始试验记录重新计算，不把人工注入的故障冒充真实生产事故。*

## 结论先行

N21（*Recovering Incomplete TypeScript Build Outputs Without Rebuilding Intact Projects*）的**可在当前独立环境完成的受控编译、故障注入、真实工具对照、跨编译器和安全性实验已经执行并留存原始证据**：总计 920 条有唯一键的主矩阵及重复试验记录，校验程序报告 920/920，无缺失、重复或内置正确性违例。

**这不等于已具备“完整 FSE Industry 论文投稿证据”。** 当前已在真实 GitHub-hosted runner 上三轮执行 `Attest/typescript-cache-action`，但仍没有企业/组织自然发生的部分恢复事件及原始流水线记录、能估计故障率的生产构建分母、生产规模的时延与业务成本。只能提出“在人工控制的不完整输出条件下，哪些恢复方法正确、何时值得选择”的有限研究结论；不能宣称工业故障发生率、部署 ROI 或“新发现 TypeScript 缺陷”。

## 研究问题与实验单位

| 研究问题 | 观测量 | 实证结果概述 |
|---|---|---|
| RQ1：编译成功是否意味着输出完整？ | tsc 退出码、逐文件路径与 SHA-256 | 在 77 个**有损注入设置**上，未强制增量 `tsc -b` 与干净真值一致 **0/77** |
| RQ2：修复范围与正确性如何权衡？ | 同一注入设置下的 8 种策略、重编译源码单元代理指标、计时 | 输入守卫 SHA 选择修复 **77/77** 正确；完整清理 **77/77** 正确；强制整组 **64/77** 正确，无法清走额外旧产物 |
| RQ3：现有工具的完整缓存恢复是否更强？ | 真正执行 Wireit 和 Turborepo；命中/禁用缓存 | 两种工具在有完整本地缓存时都 **4/4** 恢复成功；对比缓存不可用时的增量状态残留 |
| RQ4：机制是否经得住输入漂移、版本和引用闭包？ | 回拨 mtime 但改内容、TS 6、两个原生引用项目例、TS 官方源码引用子图 | SHA 仅校验输出会在输入变化时失败；输入守卫回退干净编译；TS 6 额外 30 次样本、引用图收益异质 |

研究对象来自 **7 个真实上游代码仓库**，在 4 组工作区里构成 **13 个 TypeScript 项目单元、297 个源码文件单元、604 个编译输出文件**。其中四个真实开源库被组合进**研究人员搭建**的同一工作区；另外两组是上游已有的 project references 示例；第四组为 TypeScript 5.9.3 自身 `compiler → jsTyping → services` 的 252 个源码文件引用子图。不得把人工搭建的工作区称作其原生工业 CI 配置。

**完整矩阵构成：** 主试验 100 个设置（77 个有损注入、23 个负控）× 7 种策略 = 700 次；对同一 100 个设置追加输入守卫策略 = 100 次；另在种子 29/43 上针对 4 个项目、3 类故障、5 种策略重复 120 次。主表仅纳入种子 17 的同一组 **77 个受损设置**，因此避免了不同策略分母不一致的问题。

### 注入与独立真值

七种实际改变产物的故障：删除非入口 `.js`、删除入口 `.js`、删除 `.d.ts`、修改 `.js` 字节、修改 `.d.ts` 字节、插入多余旧产物、删除整个产物目录。负控为未注入故障，以及删除构建状态文件。每次从同一干净已编译快照复制出新试验目录，故障之后执行指定策略，核验**完整路径集合与每个文件的 SHA-256**。受控项目先作独立干净编译并要求与起始输出完全一致；`.tsbuildinfo` 被视作状态，而非业务编译产物。

## 主结果：同一 77 受损设置的八策略配对比较

| 策略 | 与独立干净编译逐文件相同 | 重编源码单元中位数† | 本机修复秒数中位数 |
|---|---:|---:|---:|
| 默认非强制 `tsc -b` | 0/77 | 0 | 0.18 |
| 仅比对路径的产物清单 | 55/77 | 2 | 1.11 |
| SHA-256 产物清单、选择性修复 | 77/77 | 3 | 1.48 |
| **输入守卫 + SHA-256、选择性修复** | **77/77** | **3** | **1.74** |
| 删除全部 `.tsbuildinfo` 后构建 | 64/77 | 4 | 3.00 |
| 删除全部输出与增量状态、干净构建 | 77/77 | 4 | 2.98 |
| 整组 `tsc -b --force` | 64/77 | 4 | 3.05 |
| 完整本地缓存快照恢复（条件理想基线） | 77/77 | 0 | 0.01 |

†“源码单元”= 编译日志中报告重建的项目所含源码文件数之和，不是指令数或 CPU 工作量。计时含检测/哈希/修复，是单一共享机器的探索性测量，不是生产 CI 性能。完整缓存基线假设可取得正确、完整的已存快照，不能把该条件推广到缓存丢失的场景。

### 收益边界与异质性

输入守卫的 SHA 方案与干净构建在全部 77 个主受损设置中都正确。逐设置配对的**重编源码单元减少比例中位数为 51.35%**，所省本地时间的配对中位数为 **1.23 秒**；67/77 次重编的源码单元更少，但仅 **57/77 次**实际更快。不能用“两个策略各自计时中位数之差”充作配对中位数。

| 工作区 | 受损设置 | 减少源码单元比例的配对中位数 | 本地配对省时中位数 | 更快的设置 |
|---|---:|---:|---:|---:|
| 四个组合开源库 | 28 | 75.7% | +1.86 秒 | 27/28 |
| andrewthauer 引用项目 | 26 | 50.0% | +1.13 秒 | 22/26 |
| Quramy 引用项目 | 14 | 12.5% | **−0.37 秒** | **1/14** |
| TypeScript 自身引用子图 | 9 | 30.9% | +10.73 秒 | 7/9 |

这不是“所有项目都变快”的故事。TypeScript 官方大子图的下游项目可以少编 78/84 个上游源码单元，而触发 `compiler` 本身或 Quramy 的核心引用项目时，引用闭包和检测成本会抵消收益。以工作区为单位做留一组分析，整体源码单元节省比例中位数随删除组别变化为 **30.9%–64.9%**。仅 4 组工作区、同项目重复故障，**不进行工业总体置信区间、显著性检验或因果 ROI 推断**。

## 已实际执行的强基线和消融

1. **Wireit 0.14.12**，两个真实库 ×（删除 JS / 内容损坏）× 3 种配置，共 12 次：完整本地缓存命中 **4/4** 恢复；无本地缓存、`clean=if-file-deleted` **0/4** 恢复；无缓存但 `clean=true` **4/4** 恢复。不能称 Wireit 在已命中完整缓存时不正确。
2. **Turborepo 2.6.0**，相同 4 个故障设置×两个缓存条件，共 8 次：显式正确配置输入、输出和 `.tsbuildinfo` 时，本地缓存可用 **4/4** 恢复；强制缓存未命中且遗留增量状态 **0/4** 恢复。另一套不完整地声明 inputs 的人工 fixture 导致缓存键变化，该配置实验原始记录单独归档，**不纳入正常缓存命中结论**。
3. **SHA vs 路径存在性消融：** 内容损坏而路径仍在会让路径策略漏报；删除/多余产物等路径不一致才可触发它。主结果中，路径清单 **55/77**、SHA 清单 **77/77**。
4. **增量状态清除 vs 清理产物：** 仅强制全量编译或删除增量状态在 13 个“多余旧产物”设置中依然不清除旧文件，因此为 **64/77**；真正清理输出目录为 **77/77**。
5. **输入变化安全测试：** 3 组工作区使用真实源码字节改变、再将修改时间回拨一小时，5 种策略 × 3 = 15 次。普通增量、仅 SHA 输出验证均 **0/3** 正确；输入指纹不一致后回退全量干净编译、直接删状态、直接干净编译均 **3/3** 正确。当前输入守卫只覆盖实验中的源码/配置/锁文件；实际产品部署仍必须将解析依赖、编译器二进制、环境和影响输出的配置纳入可信输入身份。
6. **跨编译器和机制测试：** TypeScript **6.0.2** 新建独立干净编译真值，在两个真实库、三类受损设置与五种策略中完成 30 次；SHA 恢复、干净构建、完整快照 **各 6/6** 正确，非强制增量 **0/6**。另以 TS 5.9.3 和 6.0.2 真实 Compiler API 逐步验证“首次产物存在 → 删除输出但保留状态后不再出现 → 同时清状态后恢复”，两版本均复现，不可称为仅 TS 6 新引入的问题。

### 真实 GitHub-hosted runner 的新补充（2026-11-18 审计）

公开只读审阅 [Wireit 每日测试真实 GitHub Actions 缓存服务的工作流](https://github.com/google/wireit/actions/workflows/test-real-github-actions-cache-service.yml)，在 **2026-11-01 至 2026-11-17 UTC**，REST API 列出连续完整 **17 次计划执行**，全部有对应的 Ubuntu 22.04 hosted runner 作业日志。记录显示该工作流的缓存服务回归测试 **17/17** 成功，`actions/setup-node` 的 **npm 依赖缓存 17/17** 命中；后者恢复体积中位数 **61,985,947 字节**，真实缓存回归测试步骤的运行耗时中位数 **62.5 秒**。17 个确切 run/job ID、提交、日志可回溯 URL 和逐运行测量在 `results/public_ci_observability.json`。

**这些事实不等于 N21 故障率/收益：** 该测试工作流没有记录编译输出的路径和 SHA 真值，且 ~59.1 MiB 属于 **npm 依赖缓存而非 TypeScript 输出缓存**。因此不能把“17 次 CI 均成功”重新标注成“17 次无部分恢复故障”，更不能推算故障比例或生产 ROI。它只证明公开 GitHub Actions 运行记录可审计，且给出一个**不同任务**上的真实 runner 环境与时间/传输参照。

### Attest 的真实执行：3 轮 / 45 个 hosted job / 42 条对照记录

已在用户授权的专用公开仓库 [shjdjjfi/FSE-EXP-1](https://github.com/shjdjjfi/FSE-EXP-1) 的 `n21-fse-benchmark` 实验分支运行实际 `Attest/typescript-cache-action`，固定顶层提交 `7227052c996c38afb0aece6e05d185b2d45a28a5`。三轮有效运行分别是 [#44237916114](https://github.com/shjdjjfi/FSE-EXP-1/actions/runs/44237916114)、[#44238758566](https://github.com/shjdjjfi/FSE-EXP-1/actions/runs/44238758566) 和 [#44238773494](https://github.com/shjdjjfi/FSE-EXP-1/actions/runs/44238773494)。每轮 1 个独立干净构建并保存完整与人工不完整缓存的作业、14 个真正调用复合 restore action 的 Ubuntu 22.04 作业；合计 **45/45 个 runner 作业成功结束**，保存 **45 份完整原始 job log、45 份工件 ZIP、REST API run/job/step 元数据及 42 条策略指标**。逐文件路径和 SHA-256 由单独冷编译形成的真值独立核验，三轮 fixture 源码哈希完全相同。

**42 条对照中 30/42 正确，12/42 的不正确全部属于预先规定的失败对照，并非 CI job 失败。** 真实缓存命中时，研究人员预先存入的部分不完整缓存经 Attest 恢复后，普通非强制增量编译仍可能保持缺文件；对人为损坏的 `.d.ts` 或多余旧输出也有相应风险。输入守卫 + SHA 选择性修复对本矩阵所测的 5 个条件 **15/15** 完整；完整缓存、无损负控中 Attest 原样使用 **3/3** 正确，缓存未命中时普通编译 **3/3** 正确。不能据此指责 Attest 自身“造成”原始缓存不完整。

| 真 runner 配置（各 3 轮） | 仅 Attest + 普通增量 | SHA 守卫 | 强对照 | 修复时间中位数（秒，SHA 守卫 / 强对照） |
|---|---:|---:|---:|---:|
| 完整缓存、无损 | 3/3 | 3/3 | — | 0.222 / — |
| 人工部分缓存缺失 | 0/3 | 3/3 | 清理构建 3/3 | 1.254 / 1.702 |
| 恢复后 `.d.ts` 人工损坏 | 0/3 | 3/3 | 清理构建 3/3 | 0.901 / 1.594 |
| 恢复后额外旧输出 | 0/3 | 3/3 | 强制构建 0/3 | 0.972 / 1.833（强对照仍不正确） |
| 缓存故意未命中 | 3/3 | 3/3 | — | 1.607 / — |

每个小 fixture 仅 **2 个 TypeScript 项目、4 个产物文件**；各真实缓存 restore 的压缩传输体积约 **3.85–3.91 KB**，SHA 扫描量最多 **369 字节**，成本量级完全不足以代表生产流水线。45 个 job 的 GitHub REST 起止时间总和约 **789 秒（13.15 runner-job 分钟的粗粒度使用量代理；不是平台计费数据）**。真实 hosted runner 计时具有不同实例间波动：例如清理重建受损声明文件的耗时在 1.300–3.327 秒之间。完整缓存无损时，守卫额外工作中位数约 **0.080 秒**；仅在玩具式“两状态”成本假设下，**假设理想基线可以零成本预知哪些作业需要清理**、其他条件固定，部分缓存损坏与 `.d.ts` 损坏的代数盈亏平衡受损比例分别约 **15.1%** 和 **10.3%**，**不是观测到的真实故障率，更不是工程 ROI**。这一理想基线需要额外检测，因此阈值只能当作示例化敏感性分析。

首次试运行 [#44237397496](https://github.com/shjdjjfi/FSE-EXP-1/actions/runs/44237397496) 已透明排除其性能计数：原始输入指纹错误地包含输出目录中的 `.d.ts`，使人为输出损坏误触发输入漂移全量回退。保留其 15 份原始工件供复核，修复脚本并通过本机 16-case 冒烟后才执行上述三轮有效远程矩阵。逐作业时间、真实缓存服务命中、传输量、CPU/哈希负担、原始日志哈希、每个指标与代码在 `results/github_actions_aggregate.md` / `.json` / `.csv` 及 `results/github_actions_run_<ID>/`。本实验补齐了**真实 Actions 工具对照与小规模 runner 的机制计时**，仍不等于工业场景部署实验。

## 公开问题证据的界限

从目标定向搜索与 GitHub API 获取并审阅 7 个公开问题/PR，其中 5 个与缺失产物或过时输出密切相关，2 个只涉及输入依赖/诊断失效，不能混入核心事件数。有关线索包括 [TypeScript #30602](https://github.com/microsoft/TypeScript/issues/30602)、[#50646](https://github.com/microsoft/TypeScript/issues/50646)、[Nx #35079](https://github.com/nrwl/nx/issues/35079)、[Nest CLI #3312](https://github.com/nestjs/nest-cli/issues/3312) 与 [Wireit #905](https://github.com/google/wireit/pull/905)。公开 issue 的非随机样本、提问与维护者讨论**不构成真实 CI 故障频率估计**。无完整自然执行轨迹，亦不得由 issue 状态推断相关修补是否在所有部署生效。

进一步核验到 [TypeScript #30602 的一位亲历者评论](https://github.com/microsoft/TypeScript/issues/30602#issuecomment-478796641)：评论者明确回忆并行开发分支中，缓存 TypeScript buildinfo 的 CI 构建受到实际错误的影响。这可以列作 **1 条自然 CI 影响的第一人称定性陈述**，但没有原始 workflow run/job 标识、缓存快照、完整日志或独立输出清单，故不是 1 个可复盘的定量故障样本。GitHub 对公开 Actions 日志/工件的[默认保留期为 90 天](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)，老事故的日志很可能已超出保留范围。精确证据层级与不可识别的分子/分母记录在 `results/public_ci_incident_evidence.json`。

| 投入产出和工程决策 | 有小 fixture 的条件式成本阈值模型；**无实际部署投入、故障损失及工业 ROI** | 结合真实故障分母、人工维护工时、存储/运行成本与工程团队决策，估计可审计的真实投入产出 |

因此：**这套归档可以支撑初稿中的实验方法、图表、机制复现、强基线对照与负面结果；在取得工业合作证据之前，不宜把稿件包装成“完成了全部 FSE Industry 投稿实验的工业实证研究”。** 若无法取得数据，应将研究主张收窄为受控软件构建工具的边界研究，重新判断 Industry track 适配度。
